## 2. Proposed isolated staging architecture

Use a separate, access-restricted staging environment with fictional records first. The proposed shape is:

```text
Approved reviewers -> HTTPS ingress / access restriction
                    -> Node application + runtime Chromium
                    -> private network PostgreSQL endpoint
Operator-only migration job -> same staging database, separate role
Backup service -> encrypted recovery storage + separate key/access controls
Application / DB / backup signals -> restricted monitoring and operator alerts
```

This is a proposed managed PostgreSQL architecture, not a selected provider. The owner must select the account, provider, region/data residency, domain, budget, operational owner and permitted reviewers. No portfolio service is implicitly selected. Start with one application process for a measurable baseline; test multiple processes against the same network database before permitting scale-out. Never share a PGlite directory between replicas or mount the local demo database into a hosted service.

The hosting runtime must support a long-running Node service and headless Chromium, with measured CPU/RAM, temporary storage and termination grace time. Build one reproducible artifact using the lockfile and a pinned supported Node version compatible with the repository's `>=22` engine requirement. Record the exact commit, dependency/browser versions, artifact digest and migration checksums. The current `start` command executes TypeScript via `tsx`; final runtime packaging and included dependencies must be chosen and tested rather than assuming a compiled server bundle exists.

Keep staging separate from later production: different database, credentials, cookie origin, backup namespace, encryption access, logs and deployment identity. Restrict database access to approved service/operator paths. Deny public database access where the selected network architecture permits it. Do not reuse `.local` demonstration passwords, production credentials, customer files or Zoho credentials. Any later sanitized production-like dataset requires separate authorization and a documented sanitization check before staging use. Synthetic seed scripts must never run against customer data.

Before accepting the network adapter, verify rollback and commit behavior with concurrent independent connections: same-actor duplicate keys, same executive check-in races, two executives at one shop, checkout retry after lost acknowledgement, assignment/version races, report snapshot consistency, audit-write failure and connection loss. A transaction must stay on one checked-out connection. Decide pool size across **all** processes and migration/backup operations; record DB connection headroom and query/lock timeouts. Preserve parameterized SQL and UTC session configuration. Do not automatically retry a mutation with a new idempotency key after an uncertain commit.

## 3. HTTPS, configuration and secret controls

Proposed deployment requirements, to be implemented and verified:

- One canonical exact HTTPS `APP_ORIGIN` per environment; no wildcard Host/Origin acceptance. Ingress must reject unknown hosts and preserve the expected Host to the application. Test canonical navigation, sign-in, logout, all mutations, downloads, hostile Host/Origin, missing Origin, CSRF rejection and redirect behavior through the actual ingress. Do not relax these checks merely to make a proxy pass.
- Force HTTPS at ingress; enable `COOKIE_SECURE=true`; verify Secure/HttpOnly/SameSite behavior in a browser, session expiration and logout. Choose HSTS policy after HTTPS/domain review. Retain no-store for authenticated responses and exports. No private API/report response may enter a shared CDN cache.
- Keep the application listener private. Retaining a loopback application behind a same-host proxy may suit one topology; a container topology may need a deliberate bind change. Either requires reviewed hosted configuration and tests. Do not bypass the existing production guard without the replacement validation and release controls.
- Document trusted proxy hops and strip client-supplied forwarded headers at ingress. Current code does not trust `X-Forwarded-For`; implement and test any future trusted-IP extraction. Test both distributed credential attacks and shared office/mobile NAT use before accepting login limits. Add ingress rate/request/connection controls without allowing attackers to supply their own trusted address.
- Use environment-scoped secret management with audited access. Keep DB credentials, backup keys, recovery credentials and service tokens out of Git, logs, screenshots, build artifacts, exported evidence and command-line history. Use distinct runtime, migration, backup and emergency identities; rotate and rehearse rotation. `.env` being ignored is not a secret-management or encryption control. Current sessions are opaque database-backed tokens; do not invent a nonexistent JWT signing-key requirement.
- Require encrypted DB transport with certificate chain **and hostname** verification, including failure tests for wrong CA/hostname. PostgreSQL documents these semantics for libpq's `verify-full`; the eventual JavaScript driver must be configured and tested for equivalent verification using its own documented options. [PostgreSQL SSL support](https://www.postgresql.org/docs/current/libpq-ssl.html).

## 4. Identity operations and least privilege

**Owner decisions:** retain application-managed passwords with implemented operational controls, or separately scope a hosted identity integration. Decide privileged-user MFA/SSO, enrollment delivery, identity verification, recovery approvers, session duration and a named backup administrator. No identity provider is chosen here.

For application-managed accounts, implement and rehearse these workflows before real access:

1. An authorized administrator approves a named person, organization and minimum role. Deliver initial enrollment securely; do not share accounts or send reusable passwords in repository artifacts. The current operator bootstrap selects the first organization and is a local tool, not an approved multi-environment provisioning system. Admin API creation exists but is not a complete invitation lifecycle.
2. Recovery requires verified identity through an approved channel, an authorized operator and an audit record. Implement a short-lived, single-use reset/enrollment mechanism or another explicitly reviewed procedure; avoid revealing whether an email is registered. Never recover by exposing a stored hash/password or by reusing demo credentials. Test expiration, replay, rate limits and unauthorized reset attempts.
3. Password reset or suspected compromise revokes existing sessions, rotates affected credentials and records the action without storing reset secrets in audit/logs. Session revocation and password-change operations are missing today. Review scrypt parameters under the target CPU/concurrency load rather than assuming local defaults satisfy hosted throughput.
4. Offboarding disables the account and revokes sessions promptly; preserve historical attribution and audit. Explicitly reassign shops/follow-ups through approved authority, with a reason. Resolve open visits/duty only through an approved correction policy; disabling a user must not silently fabricate checkout/end times. Test existing-session rejection, role changes and denied recovery after offboarding.
5. Maintain a controlled emergency administrator procedure, access log, post-use review and rotation. Do not leave a broad database-owner credential in the application for emergency convenience.

Use separate PostgreSQL owner/migration, application and backup roles. The runtime role must have only the specific schema/table privileges needed for the application, no superuser, role/database creation, table ownership, schema modification or bypass-RLS capability. Grant audit INSERT and required SELECT, not UPDATE/DELETE; preserve the immutable trigger. Migration ownership must be outside the runtime identity. Inventory required CRUD privileges explicitly, including session cleanup, login attempts and idempotency records, and run the full suite under the restricted role. PostgreSQL privileges are independently grantable; object ownership carries additional authority. [PostgreSQL privileges](https://www.postgresql.org/docs/current/ddl-priv.html).

The trigger is an application-level append-only safeguard, not proof against a privileged DB owner. Keep operator actions and backup access in a separately protected operational audit trail. If stronger tenant isolation/RLS is later required, scope and test that change explicitly; do not claim it already exists or rely on an admin bypass role to test it.

## 5. Privacy and retained data

Before any real-data staging use, the owner must approve the allowed data categories, purposes, access roster, residency, retention/deletion periods and customer/staff notice. This plan does not determine legal requirements. Existing records can include contact names/phones, notes, visit GPS availability/coordinates/accuracy, staff activity, duty history and full before/after audit details. GPS data can also occur in audit records, so restricting a single visit field is insufficient.

Proposed controls: synthetic staging by default; least-privilege reviewer access; no continuous location tracking; no request bodies, passwords, cookies, CSRF values, precise locations or customer notes in operational logs. Current server comments prohibit those log values but unexpected-error logging includes `error.message`; review actual database/driver error redaction before hosted use. Apply retention rules to primary tables, audit, idempotency responses, logs, exports, quarantine and backups. Do not directly delete immutable audit to implement retention: design the retention/archive process separately with historical attribution intact.

PDF/Excel downloads leave server control and contain staff/customer information. Approve who may download, where files may be stored, their retention and any onward sharing. Keep test evidence synthetic/redacted. Restrict browser temporary directories and diagnostic dumps, clean them after jobs, and avoid storing PDFs as public objects. Explain how expired/deleted information ages out of backup retention and prevent a later restore from unintentionally reviving offboarded accounts or restricted data.

## 6. Encrypted backups and recovery targets — proposed, untested

**No hosted backup or restore has been configured or tested.** Assign a recovery operator plus alternate and an owner authorized to declare an incident/cutover. Proposed acceptance targets below are approval requests, not service promises:

Phase 4 separately executed an **isolated local cold-copy restore**, recorded in [restore/result.json](../evidence/phase4/restore/result.json). It closed a disposable PGlite writer, copied and hash-verified 1,044 database files, reopened an independent restored copy, compared all 14 listed table digests plus indexes/migration checksums, and rechecked the untouched temporary source. The data included 700 fictional shops, a completed visit/follow-up, duty/break history, audit, idempotency and a real hashed local session. Temporary source/backup/restore directories were removed. This is not encryption/PITR, a running-demo backup, a hosted failover or a passed hosted RPO/RTO drill. The future hosted steps below remain not-run.

| Item | Proposed target / decision |
| --- | --- |
| RPO | At most 15 minutes of acknowledged committed data lost, measured from the simulated incident to the latest recoverable committed marker. Owner must approve loss tolerance. |
| RTO | At most 4 hours from incident declaration through validated access restoration, including operator access, restore, verification and cutover. Owner must approve downtime tolerance and support hours. |
| Recovery window | 7 days of point-in-time recovery plus daily encrypted recovery copies retained 30 days; confirm actual selected-service capability and privacy retention approval. |
| Protection | Encrypt DB storage, snapshots/log archives and exported recovery copies at rest and in transit; keep decryption/recovery access separate from ordinary app credentials and test key access. |
| Drill frequency | Before hosted acceptance, after material DB/migration/backup changes, and monthly thereafter; recovery operator and alternate participate. Approve cadence and retained evidence period. |

Select a managed base-backup/WAL or equivalent PITR facility that can meet the approved target, including archive-lag monitoring. PostgreSQL PITR requires a base backup plus the needed continuous WAL sequence; a logical dump is not a WAL-replay backup. Validate selected-service restore granularity, retention, key availability and regional failure coverage before relying on it. [PostgreSQL continuous archiving and PITR](https://www.postgresql.org/docs/current/continuous-archiving.html).

Use reviewed logical exports as an additional portability/reconciliation layer when needed, with encryption and restricted storage. PostgreSQL `pg_dump` takes a consistent single-database export; global roles/configuration need separate handling, and archive formats require `pg_restore`. A successful export or backup-job status is not restore evidence. [PostgreSQL pg_dump](https://www.postgresql.org/docs/current/app-pgdump.html).

Maintain a recovery manifest: environment/database identifier, backup ID, base/WAL coverage or snapshot time, key reference (never key material), integrity/checksum metadata where supplied, source commit/artifact digest, DB/tool versions, migration names/checksums, role/configuration definitions and operator-access prerequisites. Back up approved configuration/role definitions separately from secrets; confirm secret/key recovery without copying plaintext into the manifest. Recovery storage must not be removable by the ordinary application identity. Decide independently protected recovery copies and retention locks appropriate to the approved threat model.

### Restore drill and incident runbook

The steps below are a **future rehearsal procedure**. Provider-specific commands, exact identifiers and access paths must be filled in after selection; placeholders are not executable readiness evidence.

1. **Prepare a measurable drill.** Use synthetic staging data. Record operator, reviewer, exact source/target, commit/digest, versions and migration hashes. Create timestamped committed marker records and representative visits, follow-ups, assignments, audit/idempotency and overnight duty/break data through authorized test paths. Capture expected counts/key records before the simulated incident. Identify a known good PITR target and an intentionally later bad change; record UTC times and UAE business dates.
2. **Declare and contain.** Record declaration time (RTO clock start), incident time and last acknowledged marker. For an actual incident, suspend writes/traffic, retain the original database and logs for investigation and prevent two writable primaries. For a rehearsal, simulate containment without touching production. Confirm approved operator access to backup storage and decryption keys from the recovery path, including the alternate operator.
3. **Restore into a fresh isolated target.** Verify environment/database IDs and selected backup/target timestamp before invoking the approved restore procedure. Never overwrite the source or restore over production for a drill. Confirm backup integrity and required log continuity, restore completion, expected DB version/extensions and intended roles/configuration. For encrypted exports, verify authenticated decryption/integrity before the separately reviewed restore. Keep ingress closed and outbound integrations disabled.
4. **Match application and schema.** Select the application artifact compatible with the restored schema. Compare the complete migration/checksum manifest; do not blindly run new migrations on the restored evidence. If recovery requires a forward migration, rehearse it on a separate copy and preserve the original restored target. Confirm restricted grants and audit trigger behavior.
5. **Validate recovery.** Reconcile organization/table counts, newest recoverable committed marker and absent post-target bad change. Check foreign keys, same-organization provenance, one open visit per executive, several executives at a shop, one open duty/rest interval, chronological events, historical visitors/owners and pending follow-ups. Compare expected audit actions and idempotent retry behavior. Test manager/executive isolation, fresh login, shared history, UAE dates, report totals and complete Excel/PDF generation. Reapply the approved session revocation/offboarding state after restore so restored sessions or older account status cannot reopen access. Record any deliberately lost transactions and reconciliation work.
6. **Measure and decide.** Record latest recovered acknowledged commit (actual RPO), restore/verification timings, projected or actual access-restoration time (actual RTO), warnings and evidence links. A drill passes only if approved targets and all checks pass. A failed drill produces a remediation owner and repeat drill; do not label backups recoverable merely because a job succeeded. For an actual cutover, the authorized owner approves the exact verified target, data-loss/reconciliation statement and traffic change.
7. **Cut over once, then review.** Keep the old source fenced, change only the approved application connection/traffic target, rotate affected credentials, invalidate sessions as required and run restricted smoke tests. Confirm no split writes, monitor errors/locks/report capacity and reconcile work after the recovery point. Record decision, actor and times. Securely retain or expire rehearsal targets/evidence under the approved policy; do not leave restore copies publicly accessible.

Required drill record fields: `status=not-run|failed|passed`, date, operator/reviewer, source/target IDs, backup/recovery-point ID, manifest, start/finish/cutover times, latest recovered marker, measured RPO/RTO, reconciliation results, access/session checks, report evidence, deviations and explicit approval. **Initial status for this plan: not-run.**

For the existing local demonstration only, continue the documented stop/close/copy/reopen procedure in [MIGRATION-AND-RELEASE.md](MIGRATION-AND-RELEASE.md). Do not use a live filesystem copy of a hosted PostgreSQL/PGlite data directory as a substitute for the selected backup mechanism. Do not run `pg_dump` against a local PGlite path as though it were a configured network server.

## 7. PDF runtime and capacity acceptance

Implementation details that matter operationally:

- `pnpm pdf:setup` installs Chromium locally; browser binaries are not committed. Playwright requires browser binaries matched to its package and browser OS dependencies. Build and smoke-test the exact locked package/browser combination in the final image; install during controlled image build, not the first live download. [Playwright browser installation](https://playwright.dev/docs/browsers).
- Each accepted render launches a browser. The `active >= 2` guard is a module variable in one Node process and returns `503 PDF_BUSY`; there is no queue or fleet-wide limit. With N processes, up to 2N renders can enter this guard, and report data preparation occurs before it. This does not bound all database/Excel/report work.
- Launch, HTML loading and the PDF generation race each use 30-second limits at different stages; font readiness and browser cleanup are additional work. This is not a 30-second end-to-end service guarantee. Measure full request time and cleanup after timeout/disconnect; align ingress and termination limits without masking leaks.
- Reports reject more than 10,000 primary records; duty records can contain many nested breaks. The local row/date limits and existing Unicode examples do not establish hosted maximum memory, output size or duration.
- Keep escaped HTML, disabled JavaScript, restricted CSP and blocked browser networking. Review Chromium sandboxing on the selected runtime: running the browser as root disables its sandbox in the documented Docker setup. Use an unprivileged service identity and verify the final container isolation, browser launch behavior and process cleanup; the current code does not establish a hosted sandbox guarantee. [Playwright Docker guidance](https://playwright.dev/docs/docker).

Proposed load rehearsal: run the real HTTPS service with the chosen DB/CPU/RAM/process count and synthetic realistic history. Exercise all three report types with Latin/Arabic/Malayalam, long text, repeated breaks, empty results and near-limit exports. Run one render, two simultaneous renders, a third overlapping request, repeated bursts, mixed Excel/PDF plus field mutations, and multi-process load if proposed. Include missing browser/font, blocked egress, launch failure, render timeout, browser crash, disconnected clients and application termination.

Capture end-to-end p50/p95/max latency, 503/timeout rates, bytes/pages, Node and Chromium RSS, CPU, temporary space, child-process counts, DB pool/lock wait, ordinary mutation latency and recovery after failure. Verify a third render gets the documented busy behavior, slots recover, reports reconcile, unauthorized users are denied and normal field writes retain integrity. Proposed initial review thresholds: no OOM/leaked browser processes/corrupt or truncated output, no unintended writes, ordinary API p95 under 2 seconds and typical report p95 under 15 seconds at the approved staff workload. Owner/engineering must approve representative concurrency, maximum export support and latency thresholds after measurement; these numbers are not current benchmark results. If capacity fails, separately design admission/rate controls or a bounded worker queue and retest before increasing replicas or limits.

## 8. Monitoring and operational response

Current code returns request IDs and logs unexpected errors, but provides no implemented hosted health/readiness endpoint, metrics pipeline or alert routing. Add private health/readiness checks and structured, redacted operational telemetry as separately authorized implementation work. Readiness should verify expected schema and database reachability without exposing credentials; do not use a public customer/report query as a health response.

Proposed signals and initial alerts, to tune during rehearsal:

| Signal | Initial trigger / response |
| --- | --- |
| HTTPS availability/readiness | Two consecutive failed one-minute checks: alert primary and alternate; inspect ingress/app/DB before restarting or cutting over. |
| API failures/latency | Unexpected 5xx above 1% over five minutes with a minimum 20 requests, or p95 above 2 seconds: correlate request IDs and release/DB changes. Expected validation/conflict responses need separate counts. |
| Authentication/security | Spikes in login failures/429, Host/Origin/CSRF rejections or privileged account changes: review access logs and investigate without capturing secrets or raw credentials. |
| Database | Pool exhaustion, long locks/transactions, connection failures, migration mismatch and storage growth: alert before exhaustion; use measured connection/space headroom. |
| PDF/runtime | Sustained busy/timeout/unavailable responses, browser crashes, rising child count or memory near approved capacity: protect field writes, review concurrency and dependency health. |
| Backups | Failed job, inaccessible key/storage, recoverable-point lag beyond 15 minutes or expired recovery coverage: immediate operator alert; mark the RPO unproven/breached until resolved. |
| Recovery readiness | Missed monthly drill or failed reconciliation: block release acceptance, assign remediation and repeat. |

Record who receives alerts, support hours, escalation/contact channel and who can pause writes/recover/roll back. Exercise alert delivery and alternate-operator access; a dashboard alone is not an incident process. No monitoring automation or notification subscription is created by this plan.

## 9. Release, migrations and rollback compatibility

Before a staging deployment, review the exact artifact and migration diff; retain a compatible previous artifact, tested recovery point and migration manifest. Run the migrator once using its separate identity, then start only compatible app versions. Verify a freshly initialized database and an upgraded representative database with the restricted runtime role. Keep existing migration files immutable; new changes get new versioned files. Test incomplete/failed migration behavior and prevent concurrent migration runners.

Prefer additive schema changes with a documented compatibility window; remove/rename fields only after old instances are drained and compatibility is demonstrated. Migration `003` already removes the one-open-visit-per-shop uniqueness rule, so a rollback to an older application with the superseded rule is not automatically business-compatible. Write a release-specific app/schema compatibility table and smoke tests rather than assuming Git ancestry guarantees safety.

For a code-only regression, roll traffic back only if the previous artifact is compatible with the current schema and writes. For a data/schema defect, fence writes, preserve the affected source, and choose a reviewed forward repair or the rehearsed restore/reconciliation procedure with owner authorization for any data loss. Do not drop tables, edit applied checksums or automatically apply destructive down migrations. Restoring an older database loses later accepted writes and may revive old sessions/account state; quantify and reconcile that explicitly. A Git revert alone never restores database state.

Release-specific smoke evidence must cover login/logout/revocation, executive duty/visit/follow-up writes, manager shared history/assignment, fresh-session persistence, cross-organization denials, retries, mobile/GPS permitted and denied paths, report totals/Unicode downloads and operational alerts. Owner UAT and approved business policies remain required alongside engineering evidence.

## 10. Real customer import — separate implementation and approval gate

No source file or customer list has been supplied and no import implementation exists. Before committing real records:

1. Name the authorized data owner, source, target environment/organization and import actor. Preserve an immutable source checksum, source row IDs, acquisition time and permitted retention. Keep raw files in encrypted restricted quarantine, outside the served directory and ordinary logs. Define file type/size limits and parser behavior; never execute spreadsheet formulas or silently truncate input.
2. Review explicit field/assignee mapping. Validate required fields, text/length limits, canonical statuses, phone normalization, source identifiers and active same-organization executive IDs. Do not match real staff to fictional demo names. Quarantine invalid/ambiguous rows with safe row-level error reports; correct and revalidate without silently discarding rows.
3. Review exact-ID/normalized-phone duplicates and cautious name-plus-area candidates. Names alone cannot approve an automatic merge. Record create/update/skip/merge decisions; preserve existing visits, follow-ups, attribution and assignment history. Require separate policy approval for merging or historical data changes.
4. Implement a non-writing dry run with counts for total, accepted, rejected/quarantined, duplicate candidates, skipped and proposed updates, plus target before/expected-after counts. Reconcile every input row to one disposition and preview representative records. Prove the dry run does not alter domain/provenance/audit records in the target.
5. Present the exact target, source checksum, parser/mapping version, reviewed row/duplicate decisions, dry-run report, retention policy, verified backup/recovery point and rollback impact for **specific authorized commit approval**. Revalidate if source, mapping, target state or decisions change. Staging approval or report-download permission does not authorize customer import.
6. Implement replay-safe transactional commit with the reviewed batch checksum, actor, row IDs, provenance and append-only audit; test interruption/retry and concurrent edits. Do not change the current `POLICY_PENDING` response before this tooling and policy exist. Define whether the batch is all-or-nothing or explicitly reviewed partial import; never quietly commit only valid rows.
7. Reconcile committed/skipped/rejected counts to the approved dry run and authoritative source, check assignments/history with independent executive/manager sessions, record approval and completion evidence, and quarantine discrepancies for review. Preserve the original source and rejection report under the approved retention policy. Rollback must preserve later legitimate activity; use reviewed compensating changes or recovery/reconciliation rather than blindly deleting imported shops.
