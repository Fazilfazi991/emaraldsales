# Real-data pilot preparation: not approved for deployment

The public static demonstration stores data in each browser and uses demo role switching. It must not be used for real staff or customer records. The existing hosted backend is restricted to a synthetic workspace and remains so. No real-data hosting, account creation, seeding, import, deployment, or Zoho connection is authorized by this document.

## Current engineering state

This branch adds a manager/admin-only, version-checked enquiry conversion API. It changes the existing record in place, preserving its visits, follow-ups, and owner; conversion and its non-contact audit event are committed together, and retries use the existing idempotency mechanism. Secure UI navigation separates customers and enquiries; managers can convert enquiries and managers or assigned salespeople can update enquiry status. Managers can assign unassigned records through the existing audited transfer action. Manager counts and salesperson enquiry counts use shared server records. The independent public demonstration remains separate.

Migrations 004–005 and `pilot-import.ts` provide a transactional import primitive. `pilot-workbooks.ts` reads the two Excel sheets, hashes their exact bytes, keeps numeric phones as their stored numeric value plus original number format, flags review issues, binds approved owner IDs, and can invoke the transaction only against a caller-provided database and an explicit matching review manifest. The transaction rejects duplicate source rows, unapproved/inactive owners, changed manifests, and initial import into a non-empty workspace. It retains source rows and review codes and retries a matching batch safely. Tests use fictional records only. `pilot-import-hosted.ts` prepares an operator command with explicit environment and batch approvals, manager authentication, workspace checks and pre-connection file verification. It has not been run or verified against a network PostgreSQL server. It requires independent review, a dedicated least-privilege import role, and explicit owner approval before connection or import. There is no HTTP import endpoint. `pilot-hosted.ts` is a separately gated, unconnected handler requiring a single approved organization and no synthetic shops; it is not the current Vercel entrypoint and has not been deployed. The existing synthetic hosted guard has not been bypassed.

The local preview command reads source files without writing their values to the report: `pnpm exec tsx scripts/pilot-preview.ts <customers.xlsx> <leads.xlsx> <new-private-report.json>`. Use a private ignored directory and protect the output. The report contains hashes and row references, not customer names, phone numbers or tax identifiers. The owner confirmed the three salesperson mappings, that eight missing owners stay unassigned, and that the lead contact-person formula error on Excel row 298 may be blank pending manager review. All other review flags and the exact batch still need review and approval; numeric Excel values do not prove the original leading zeros.

For a future approved batch, a private JSON review manifest must contain `sourceHash` (the preview's combined hash), `customers`, `leads`, `owners` (source label to the approved active executive's UUID), `unassignedRows` (the exact source row numbers), `reviewedIssues` (every reviewed preview issue key), and `acceptedBlankCells` (keys for formula-error cells that the owner explicitly accepted as blank). Never use fictional demo account IDs. Acknowledging a flag does not repair or normalize a phone number. For an unusable formula, the original workbook remains the source of record. The operator command also requires the same hash in `CRM_APPROVED_SOURCE_HASH`, the dedicated pilot configuration, a separate `CRM_PILOT_IMPORT_APPROVAL`, and manager credentials; do not set these or run it before the owner has approved the infrastructure and exact batch. Runtime and import credentials must be separate and privately supplied, never committed.

Migration 004 must be reviewed for the existing hosted runtime grants, migration readiness checks and backward compatibility before deployment. In particular, all uses of nullable assignments and new columns need end-to-end review. Do not apply this migration to a hosted database without approval.

## Blockers before a real pilot

- Independently review the workbook parser, mapped fields and complete row-level preview. Confirm exceptions, numeric phone handling, field lengths, provenance, duplicate handling, and operator authorization. Do not automatically merge source rows. Re-verify exact source file hashes and counts at approval time.
- Create and verify the approved roster only after the environment is approved. Link the approved source salesperson labels to actual account IDs; do not map them to demo users.
- Independently review the separate pilot handler, define account onboarding/recovery, and provision a private workspace only after approval. Keep synthetic staging isolated, including its 700 fictional shops. Confirm host-side tester access restrictions and runtime/migration/import role grants.
- Complete end-to-end verification of the secure frontend, manager assignment, staff activity and working-hours reports across independent accounts. The delivery/collection workflow must remain disabled for real users until it has a secure tested backend.
- New shop-edit audit events retain changed field names, versions and a redacted reason instead of contact values; checkout audits omit free-text discussion. Server exception logs no longer print error details. Independently review all other privacy paths and existing historical audit records before pilot release; past audit records are immutable and were not rewritten.
- Verify backup encryption, isolation and a full restore in an approved environment, followed by multi-account browser acceptance and the requested device widths. A local synthetic test is not proof of hosted restore or physical-phone testing.

## Infrastructure proposal for owner review

Use a private, isolated managed PostgreSQL database, TLS with certificate verification, and the existing server-side authenticated application hosted in a separate protected environment. Select the provider and available region jointly with the owner, agree a monthly budget cap and named administrators, restrict access to approved testers, and specify who monitors backups and performs restore drills. No provider, region, cost, access list, or backup owner has been approved yet. The exact deployment architecture and account recovery procedure require a security review; do not use the static demo for this purpose.

Before hosted import, the owner must approve the chosen infrastructure, staff roster, exact reviewed batch and its file hashes, handling of exceptions, backup/restore and retention/export procedures. Preserve original spreadsheets privately. Do not expose tax registration data in ordinary field-sales views or logs. Do not place real records, files, contact numbers, tax identifiers or private logs in the public repository.
